# A2UI messages for `air_ui`

Pass A2UI v0.9 messages as the `messages` argument of `air_ui` with `action: "present"`. The argument is a JSON array of messages. The host renders the messages with the Air catalog below.
The `present` result carries the verdict of the open view: `RENDERED`, or `FAILED` with `errors`. Each error has a `code`, the JSON pointer `path` of the failed field in the message body, a `message`, and the `messageIndex` of the failed message in your `messages`.
After `FAILED`, the view keeps its last good revision, and the host keeps none of the refused messages. Fix each named error and present the corrected messages again.
With no open view the result is `PENDING`. Read the verdict later with `action: "state"`.
The first present of a view has no `viewId`, and its result names the `viewId` of the new view. It carries `createSurface`, `updateComponents`, and `updateDataModel`. A later present of the same `viewId` carries only the messages that change the view, usually `updateDataModel`.
`action: "state"` returns the data model of the view. The data model holds the edits of the user, so read it before you change a form.
A click on a control with an `event` action sends you a prompt. Its first line is `<app>: <event name>`. `<app>` is the part of the event name before the first colon, or the view title when the name has no colon. A JSON block follows with `viewId`, `revision`, `surfaceId`, `sourceComponentId`, `context`, and `dataModel`. Answer with a new `present` call for the same `viewId`.

## Messages

- Each message is `{"version": "v0.9", "<kind>": {...}}` with exactly one kind: `createSurface`, `updateComponents`, `updateDataModel`, or `deleteSurface`.
- `createSurface: {surfaceId, catalogId}` starts a view. The `surfaceId` is a short kebab-case name. The `catalogId` is `https://jetbrains.com/air/genui/v1`.
- `updateComponents: {surfaceId, components}` adds or replaces components by `id`. `components` is a flat list of `{"id": "...", "component": "<Name>", ...props}`. A prop goes directly on the component object, not in a `props` object.
- `updateDataModel: {surfaceId, path, value}` writes `value` at the JSON pointer `path`. `"path": "/"` sets the complete data model. A message with no `value` deletes the key at `path`.
- `deleteSurface: {surfaceId}` removes the surface.
- Send the messages of a new view in this order: `createSurface`, `updateComponents`, `updateDataModel` with `"path": "/"`.
- One component has the id `root`. Put it first, and put each parent before its children.
- Each id is unique in the surface. Each id in `children`, and in each prop of the type `ComponentId`, must be the id of a component of the same surface.
- Each component must be reachable from `root`. A component that no parent names is an error, and so is a cycle.
- A component takes only the props of its catalog line, plus `accessibility: {label?, description?}`. An unknown prop is an error.

## Data binding

- Each data prop takes a literal, a data binding `{"path": "/pointer"}`, or a function call `{"call": "<name>", "args": {...}, "returnType": "<type>"}`. The `returnType` is the type that the prop needs: `string`, `number`, `boolean`, `array`, `object`, or `any`.
- In the catalog lines, `string`, `number`, `boolean`, and `string[]` are the types after the binding resolves. `DynamicString`, `DynamicNumber`, `DynamicBoolean`, and `DynamicValue` in a function line take a literal, a binding, or a function call.
- After a binding resolves, the value must have the type of the prop. A `string` prop refuses a number. A prop of the type `string | number` or `NumberValue` takes both.
- A template child list `{"componentId": "<id>", "path": "/list"}` repeats one component for each item of the list. The list must be a JSON array. Inside the template, a path without a leading slash reads the item, for example `{"path": "title"}`. A path with a leading slash reads the data model root.
- A Table takes its rows as a list of row objects, usually `"rows": {"path": "/issues"}`. Each column shows one `field` of the row.
- An input is two-way: TextField, CheckBox, ChoicePicker, Slider, DateTimeInput, the `value` of Tabs and Accordion, and the `open` of Modal. Bind it to a data path, and it writes each user edit to that path.
- A ChoicePicker `value` is always a list of option values, also for one choice, for example `["fast"]`. Use `[]` for no choice.
- Formatted text: `{"call": "formatString", "args": {"value": "${/open} open"}, "returnType": "string"}`.

## Actions

- An `Action` is an `event` or a `functionCall`, never both.
- `{"event": {"name": "<name>", "context": {...}}}` sends the event to you. Give each control that needs your work an event. A context value is a literal, a binding, or a function call, and it resolves at the click. Put the paths of the inputs in the context to get their values.
- Name an event `<app>:<action>`, for example `my-work:close`, when an app of yours owns the view. The prompt of the click then starts with the app name.
- The component adds its payload to the context. A key of your context wins. A table row action adds `{row, key, item}`: the row index, the `rowKey` field, and the row object. A cell action adds `{row, key, item, column, value}`. A Metric adds `{label, value}`, a Steps item `{index, title}`, a BarList item `{name, value, key}`, a chart click `{label, value}` (a bar chart also `series`), and `onChange` or `onSubmit` `{value}`.
- A Button in a template resolves a relative path of its context against its item, for example `"context": {"id": {"path": "id"}}`.
- `{"functionCall": {"call": "<name>", "args": {...}}}` runs with no round trip to you. `setData` and `cycle` change the data model in the view.
- The client functions run in the IDE: `openUrl(url)` opens an `http` or `https` URL in the system browser, `openFile(path, line?)` opens a file in the editor at the line, `showDiff(path)` shows the local changes of a file against its base revision, and `runConfiguration(name)` runs the run configuration with that name. A path is relative to the project directory, or absolute.
- In an app view, `appTool(name, args?, fromEvent?)` calls the tool `name` of the app server of the view, with no round trip to you. `fromEvent` maps a tool argument to a dotted field of the event payload, for example `{"id": "key"}` for a table row. `OnShow` runs its action once after its first render.

Token Reference: - Year: 'yy' (26), 'yyyy' (2026) - Month: 'M' (1), 'MM' (01), 'MMM' (Jan), 'MMMM' (January) - Day: 'd' (1), 'dd' (01), 'E' (Tue), 'EEEE' (Tuesday) - Hour (12h): 'h' (1-12), 'hh' (01-12) - requires 'a' for AM/PM - Hour (24h): 'H' (0-23), 'HH' (00-23) - Military Time - Minute: 'mm' (00-59) - Second: 'ss' (00-59) - Period: 'a' (AM/PM) Examples: - 'MMM dd, yyyy' -> 'Jan 16, 2026' - 'HH:mm' -> '14:30' (Military) - 'h:mm a' -> '2:30 PM' - 'EEEE, d MMMM' -> 'Friday, 16 January' Air: a number value is epoch milliseconds and formats in the local time zone of the IDE. timeZone local formats a text instant in the local time zone too. A text without an offset is UTC, as in the basic catalog.

## Air Host Rules

- The view has no data source and runs no tool. Use your own tools to get the data, then put it in the data model. This is false for an app view: its app server owns the data and runs the tools of `appTool`.
- Take the records, the numbers, and the names from your tools or from the request. Do not invent data. You can write your own titles, labels, and short descriptions.
- Put the records, the numbers, and the names in the data model, and bind each prop that shows them. Write titles, labels, and short descriptions as literals. A later change of the view then needs only `updateDataModel`.
- Store each value once, in the type that it has. A count stays a number, a name stays a string.
- Use an `event` action for each control that needs your work. The event name and the resolved context arrive as one prompt.
- Use a client function for an IDE step that needs no work from you, for example a button that opens the file of a row. A client function sends you nothing. In an app view, `appTool` sends the call to the app server, and the server answers with the next revision.
- The host loads no image from the network. Use an Image only with a `data:` URL. Prefer text, tables, and charts.
- Use one surface for one view, and keep each component id from one present to the next.
- A later present of a view sends `updateDataModel` messages for the values that change, and `updateComponents` only when the structure changes. To remove an item from a list, send the complete new list at the path of the list, because a delete at a list index leaves an empty slot.
- A new `createSurface` for the surface of a known view starts the view again. Send it only to replace the view completely.

## Final Check

Before each present, check:
- The messages are one JSON array, and each message has `"version": "v0.9"`.
- `root` exists, each id is unique, each child id exists, and each component is reachable from `root`.
- Each component name and each prop is in the catalog lines. Each enum value is one of the listed values.
- Each bound path exists in the data model, each template path names an array, and each value has the type of its prop.
- Each function call in a prop has `returnType`.
